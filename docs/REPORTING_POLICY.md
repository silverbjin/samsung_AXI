# Samsung AXI — 작업·문제 해결 보고서 공통 정책

- 상태: **적용** (2026-11-19)
- 목적: 구현 결과뿐 아니라 **문제 정의 → 근거 수집 → 기술 판단 → 검증 → 인수** 과정을 교육 자산으로 축적합니다.
- 적용 범위: 이 저장소의 레스토랑 ROS 2 MVP, Gazebo World, Nav2/SLAM, 센서/안전, GitHub Actions, WSL2 인수 관련 모든 변경
- 출고 조건: 코드의 정해진 검증만으로 판정하며, **문서 작성 자체가 기능 PASS를 만들지 않습니다.**

## 1. 문서를 작성하는 시점과 경로

| 시점 | 생성하는 문서 | 위치 및 규칙 |
|---|---|---|
| 작업 단위가 끝났을 때 (PASS / PARTIAL / BLOCKED) | **경과 보고서** | `docs/reports/tasks/YYYY-MM-DD_<단계>_<짧은주제>.md` |
| 개발 중 결함·CI 실패·현장 미동작을 발견했을 때 | **문제 해결 보고서** | `docs/reports/issues/YYYY-MM-DD_<issue-id>_<짧은주제>.md` |
| 같은 문제가 미해결인 채 넘겨질 때 | 기존 문제 해결 보고서에 `OPEN/HOLD`와 후속 조치 기록 | 새로 중복 보고서 생성하지 않음 |
| 문제가 해결되어 검증했을 때 | 기존 문제 해결 보고서에 수정 커밋·재검 URL·종결 판정 추가 | 같은 이슈 파일 갱신 |

한 작업에서 디버깅이 일어나면 **작업 보고서 1건 + 해당 문제 보고서 1건**을 남기고 서로 링크합니다. 여러 자잘한 증상이 하나의 원인으로 귀결되면 이슈 보고서도 하나로 묶습니다. 문제 없이 끝난 작업에는 디버깅 보고서를 억지로 만들지 않습니다.

## 2. 최소 기록 필드

**경과 보고:** 작업 ID/목적 · 작업 전 기준(commit) · 변경 파일 · 재사용/설계 판단 이유 · 실행 명령 · 기대 결과 vs 관찰 결과 · 실제 증거(링크) · 완료/미검증 판정 · 다음 경계.

**문제 해결:** 현상/영향 · 재현 환경·명령 · 실패 로그 첫 지점 · 증거와 구별한 가설 · 근본 원인(또는 미확정) · 왜 해당 수정안을 택했는지 · 변경 파일/commit · 재검 명령/Actions URL · 수정 후 실제 결과 · 잔여 위험/교육 포인트.

**판정 용어:**
- `PASS`: 해당 단계에서 정의한 실제 검사가 성공한 증거가 있음
- `PARTIAL`: 일부만 성공했고 핵심 미완료가 명시됨
- `BLOCKED` / `HOLD`: 실패 또는 외부 의존성으로 다음 단계 불가
- `NOT_RUN`: 빌드나 검사는 미실행; 성공 주장 금지
- `OPEN` / `RESOLVED`: 디버깅 티켓의 상태. `RESOLVED`는 동일 실패 경계에서 수정 확인 후만 사용

**특별 주의:** CI L0/L1 GREEN, Gazebo 헤드리스 L2 센서 PASS, Nav2 실제 주행, 강사 WSL2 GUI 인수는 서로 다른 증거입니다. 이전 단계의 PASS를 다음 단계의 PASS로 승격하지 않습니다.

## 3. Git·PR·Actions 연결

1. 작업 시작: 기존 `docs/DEVELOPMENT_LOG.md`, 관련 reports, 기준 commit/Run을 확인합니다.
2. 개발·검증: 최초 실패를 한 번 포착해 원본을 보존하고 좁은 범위로 수정합니다.
3. 작업 종료: 템플릿을 채워 보고서를 **코드와 동일한 커밋 또는 동일 PR 내 마지막 커밋**에 추가합니다.
4. PR 본문: `작업 보고서 링크 / 디버깅 보고서 링크(있는 경우) / 검증된 범위 / 미검증 경계`를 명시합니다.
5. Actions 증거가 나중에 나오면 보고서의 `CI Run / 실제 결과`를 업데이트하는 후속 커밋을 남깁니다. 판정은 그때 갱신합니다.
6. `docs/DEVELOPMENT_LOG.md`에는 날짜·작업 ID·보고서 링크·결과만 색인으로 추가합니다. 기존 기록을 삭제하지 않습니다.

## 4. 교육용 해설 규칙

훈련생이 읽고 재현할 수 있도록 아래 질문에 답합니다.

- **왜:** 어떤 요구사항/관찰 결과 때문에 이 작업이 필요했습니까?
- **어디서:** ROS 2 노드/토픽, Nav2 Action, Gazebo 모델, CI Job 중 어느 경계가 문제였습니까?
- **왜 이 해결책:** 다른 방법 대신 공식 구현 재사용/최소 수정을 선택한 근거는 무엇입니까?
- **무엇이 증거:** 로그, 테스트 명령, 주행 결과 중 무엇으로 판단했습니까?
- **무엇은 아직 모르는가:** 현장 WSL2 최종 검증 등 미검증을 어떻게 분리했습니까?

민감정보/토큰, 대용량 아티팩트, 불필요한 기기 식별값은 넣지 않습니다. 증거 링크는 권한 없이 접근 가능한 공개 Actions URL을 우선하고, 없는 경우 `NOT_RUN`으로 적습니다.

## 5. MVP 과도한 확장 방지

문서 규칙은 새 검증 게이트·임계값·다중 PC·반복 주행을 추가하지 않습니다. **기능 동작을 우선**하며, 원인 규명·최소 수정·한 번의 해당 경계 재검만 기록합니다.
